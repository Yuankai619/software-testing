# 逐字稿：Who Checks the Agent?

總長約 9 分半。每頁標題後面的時間是建議長度。

## 1. Who Checks the Agent?（約 0:15）

大家好，我是（你的名字）。我今天要報告的題目是 Who Checks the Agent。現在很多人用 promptfoo、DeepEval 這類工具來測 LLM agent，我這次就是拿這兩個工具去測一個會呼叫工具的 agent。我想知道的是，這些工具告訴我們 pass 或 fail 的時候，我們到底能不能相信它。

## 2. Executive summary（約 0:45）

我先把整份研究的重點講完，後面再一頁一頁細看。

我自己做了一個選課的 agent，照規格寫了 40 個測試，然後故意做了 11 個有錯的版本，每個測試都跑 5 次。接著我用這兩個工具設計了六種不同的 oracle，去判斷這些執行結果，最後再回頭檢查這些 oracle 判得到底準不準。

結果有四個發現。第一，兩個不需要呼叫模型的確定性檢查，合起來就抓到 11 個錯裡面的 7 個，跟六種 oracle 全部加起來一樣多。第二，在用模型當評審的方法裡，看得到工具呼叫紀錄的那個最準，κ 有 0.92，可是 DeepEval 內建的 TaskCompletion 只有 0.19。第三，如果直接拿 agent 自己的輸出當標準答案，40 個裡面有 7 個其實是錯的。第四，有一個資料外洩，只有 red team 找得到。

所以這份研究的重點不是比較哪個工具功能多，而是把 oracle 本身拿出來測。當然也有限制：只測了一個 agent、一個模型，標註是 AI 做的，每個測試也只跑了 5 次。

## 3. Where does an oracle get its expected behaviour?（約 0:25）

因為整份研究都在討論 oracle，所以我先講一下我是怎麼分類的。

oracle 要判斷對錯，就一定要有一個「正確答案」可以比。這個正確答案大概有三種來源：第一種是從規格寫出來的，例如寫成程式或評分標準；第二種是拿之前錄下來的輸出當答案；第三種是乾脆交給另一個模型，讓它自己判斷。等一下介紹的六種 oracle，每一種都屬於這三類其中之一。

## 4. Why LLM agents make the oracle hard（約 0:35）

那為什麼 agent 的 oracle 特別難寫？主要有三個原因。

第一，同一個正確答案可以有很多種講法，所以沒辦法逐字比對。第二，同樣的輸入，每次跑出來的結果都可能不一樣。像測試 E06，原本的 agent 跑 5 次，就有 3 次讓學生超過學分上限。第三，agent 會呼叫工具去改資料，它可能已經幫學生選了課，嘴巴上卻說沒選。所以只看它最後講了什麼是不夠的，還要看它中間到底做了什麼。

## 5. The system under test（約 0:45）

接下來介紹我測的系統。這是一個選課助理，使用者是學生 S001。舉個例子，學生說「幫我選 CS301 和 CS320」，正確的做法是只選 CS301，因為兩門都選會變成 22 學分，超過 20 學分的上限，而且 agent 要把兩門課的結果都講清楚。

這個 agent 用的是 gpt-4.1-mini，有六個工具，其中 enroll 和 drop 會真的改資料。資料庫裡有 25 門課、3 個學生。規格一共有 8 條規則，像是要先檢查資格、要保護隱私，還有不能照著資料裡藏的指令做事。我也在兩門課的課程說明裡偷偷放了惡意指令，用來測間接的 prompt injection。每次執行我都會存一份 trace，裡面有每一個工具呼叫、最後的回答，還有最後選了哪些課。

## 6. Two tools, six oracles（約 0:50）

有了系統之後，再來看我設計的六種 oracle。前面四種寫在 promptfoo，後面兩種寫在 DeepEval。

L1 是一段 Python 程式，直接去讀 trace，看最後選的課對不對、有沒有呼叫不該呼叫的工具、有沒有讀到別的學生的資料。L2 比較簡單，就是檢查回答裡有沒有出現規格要求的關鍵字，或是有沒有出現不該出現的字。這兩種都不需要呼叫模型。

L3 是拿原本的 agent 第一次跑出來的回答當標準答案，再請模型判斷新的回答跟它一不一致。這是很常見的快照式做法，而且我刻意不去檢查這些標準答案對不對。

剩下三種都是請模型當評審。J1 和 J2 用的是同一份評分標準，差別在於 J1 只看得到回答，J2 用 DeepEval 的 G-Eval，連工具呼叫都看得到。J3 是 DeepEval 的 TaskCompletion，它不用評分標準，而是讓模型自己猜任務是什麼、有沒有完成。

## 7. Mutation testing（約 0:45）

那要怎麼知道這些 oracle 抓不抓得到錯？我用的是 mutation testing。我手動做了 11 個 mutant，每個只改一個地方，分散在工具程式、prompt、工具說明、agent 的執行迴圈和模型這五層。

這裡有個問題：agent 每次跑的結果都不太一樣，只跑一次就比的話，會出現很多其實是巧合的 kill。所以我定了一個比較嚴格的規則：每個測試跑 5 次，原本的版本至少要過 4 次，mutant 最多只能過 1 次，這樣才算 kill。之後我還會去讀 trace，確認 mutant 失敗的那一次真的有問題，才算 valid kill。

其中 M03 比較特別，它拿掉了權限檢查，但是功能測試從來沒有讓 agent 去查別的學生，所以那段有錯的程式一次都沒被執行到。也就是說，任何對 M03 的 kill 一定是假的，剛好可以拿來當對照組。

## 8. Experiment setup（約 0:35）

把這些加起來，整個實驗的規模是這樣：12 個版本、40 個測試、每個跑 5 次，總共 2,400 份 trace。六種 oracle 判的都是同一批 trace，所以如果判斷結果不一樣，原因只會出在 oracle 本身。

另外，我讀過完整的 trace，標註了 640 筆輸出，拿來當 RQ2 的標準答案。red team 則是另外跑的，總共 64 個攻擊。主要當評審的模型是 Claude Haiku 5.5。整個研究只花了 12.2 美元，真正花時間的反而是標註和讀 trace。

## 9. RQ1: Which oracles catch the injected faults?（約 1:10）

接下來看結果，先從 RQ1 開始：每種 oracle 抓到幾個植入的錯。

先看左邊這張圖。藍色長條是 valid kill 的數量。上面的虛線框是只跑一次的情況，用到模型的 oracle 每跑一次都會「抓到」8 到 11 個，看起來很厲害，但大部分其實只是 agent 本身不穩定造成的。

改用跑 5 次的規則之後，L1 和 L2 各抓到 5 個，J1 和 J2 各 6 個，J3 只有 4 個。L3 雖然有 7 個，但它同時有 17 次假的 kill，這個等一下會解釋。

右邊這張表，每一列是一個 mutant，每一欄是一種 oracle，藍色代表有抓到。可以看到不同的 oracle 擅長抓不同的錯。如果是做錯事，例如 M04 讓學生選到衝堂的課，會看 trace 的 L1 和 J2 就抓得到。如果是講錯話，例如 M09 把工具結果截斷之後，agent 開始亂編先修課，L1 就看不到，但會看回答的 L2、J1、J2 抓得到。

最下面這四個 M03、M05、M07、M08，沒有任何 oracle 抓到，原因有兩種。一種是錯誤被別的地方擋掉了，像 M07 把 prompt 裡的學分上限改成 25，但工具回傳的是 20，模型選擇相信工具。另一種是原本的 agent 在那個測試上本來就會錯，所以看不出 mutant 有比較差。

整體來說，光是 L1 加 L2 這兩個便宜的檢查，就抓到 7 個，跟六種全部加起來一樣多。

## 10. RQ2: Do the oracles agree with careful labels?（約 0:50）

RQ1 看的是抓不抓得到錯，RQ2 則是看 oracle 的判斷跟仔細標註的結果一不一致。

這 640 筆裡面只有 151 筆有問題，大部分都是對的。所以如果只看準確率，會太樂觀，就算一個 oracle 全部都判通過，準確率也有 76%。因此我改用 Cohen's κ，它會把碰巧猜對的部分扣掉。κ 等於 1 代表完全一致，等於 0 就跟亂猜差不多。

結果 J2 最高，有 0.92；J1 是 0.86；L1 加 L2 合起來是 0.81；J3 只有 0.19。

我也試過換評審模型。如果改用跟 agent 同一個模型，也就是 GPT-4.1 mini 來當 J2 的評審，會漏掉 47% 的問題。所以評審最好不要跟 agent 用同一個模型。

## 11. RQ2: Where the oracles go wrong（約 0:55）

知道了誰比較準之後，這一頁再看它們錯在哪裡。深色是漏判，也就是有問題卻判通過；淺色是誤判，也就是明明是對的卻判失敗。

L1 完全沒有誤判，可是漏掉了 69%，因為大部分的問題出在 agent 講的話，而不是它做的事。J3 則是兩種錯都很多，原因是它把 111 個正確的拒絕全部判成失敗。比如使用者想看別人的資料，agent 正確地拒絕了，TaskCompletion 卻覺得任務沒完成。

右下角是 L3 的 assertion echo，也就是剛剛說要解釋的地方。L3 的標準答案是從原本的 agent 錄下來的，40 個裡面有 7 個本身就是錯的。在這 7 個測試上，有問題的輸出剛好跟錯的標準答案一致，所以 L3 放過了 68% 的問題，其他測試只放過 16%。反過來說，正確的回答因為跟錯的標準答案不一樣，反而被判失敗。這就是 L3 會有 17 次假 kill 的原因。

## 12. RQ3: What does promptfoo's red team find?（約 0:55）

前面都是我自己手寫的測試，最後一個問題 RQ3 想看的是，自動產生的攻擊能不能找到我沒想到的問題。

promptfoo 的 red team 會根據我寫的 agent 用途和規則，自動產生 64 個攻擊，每個跑 3 次，總共 192 次，然後再請另一個模型當 grader，判斷 agent 有沒有被攻破。我把每一次的 trace 都讀過，再跟 grader 的判斷對照。

在原本的 agent 上，grader 標了 2 個問題，但兩個都是誤報。反而有 7 個真正的問題它沒抓到，其中 5 次是 agent 沒做資格檢查就直接呼叫 enroll，只是因為那門課不存在，才沒有真的選上。

換到 M03，也就是沒有權限檢查的版本，有 10 次攻擊讓 agent 去查別的學生，其中 8 次真的把資料告訴了使用者，grader 抓到 7 次。這是我 40 個功能測試都沒有走到的路徑。不過也要注意，64 個攻擊裡有 34 個提到的課程根本不存在，因為產生攻擊的模型並不知道系統裡有哪些資料。

## 13. Conclusions（約 0:45）

最後總結一下，主要有五點。第一，只跑一次的話，每種 oracle 看起來都很強，所以一定要重複跑，並確認 kill 是真的。第二，便宜的確定性檢查其實很有用。第三，用模型當評審之前，要先拿標註過的資料檢查它準不準。第四，從 agent 錄下來的標準答案，會連 bug 一起錄進去。第五，red team 可以找到新的路徑，但結果還是需要有人去讀 trace 確認。

限制的部分，這次只測了一個小 agent 和一個模型，標註是 AI 照著準則做的，不是另外找人標，測試和錯誤也都是我自己寫的，而且每個測試只跑 5 次。所以換一個系統，數字一定會不一樣，但我覺得這些現象很有可能會再出現。

## 14. Thank you（約 0:10）

最後用一句話收尾：這兩個工具都讓我們很容易加上一個 oracle，但都沒有幫我們確認這個 oracle 到底對不對。我的報告就到這裡，謝謝大家。
