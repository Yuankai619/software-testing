# 逐字稿：Who Checks the Agent?

總長約 9 分半。每頁標題後面的時間是建議長度。

## 1. Who Checks the Agent?（約 0:15）

大家好，我是（你的名字）。我的期中報告題目是 Who Checks the Agent。我用 promptfoo 和 DeepEval 這兩個工具，測試一個會呼叫工具的 LLM agent。我想回答的問題是：這些工具判出來的 pass 和 fail，到底能不能相信。

## 2. Executive summary（約 0:45）

先講結論。我寫了一個選課 agent，依照規格寫了 40 個測試，另外做了 11 個故意放錯的版本，每個測試跑 5 次。我用兩個工具做了六種 oracle，再檢查這些 oracle 本身判得準不準。

結果有四點。第一，兩個不用花錢的程式檢查，就抓到 11 個錯裡的 7 個，跟六個 oracle 全部加起來一樣多。第二，看得到工具呼叫的 judge 最準，κ 是 0.92；DeepEval 內建的 TaskCompletion 只有 0.19。第三，從 agent 自己的輸出錄下來的參考答案，40 個裡有 7 個是錯的。第四，red team 找到一個只有它找得到的資料外洩。

這份研究的貢獻是把 oracle 本身拿來測，不只是比較工具。限制是只有一個 agent 和一個模型、標註是 AI 做的，而且每個測試只跑 5 次。

## 3. Where does an oracle get its expected behaviour?（約 0:25）

這份研究關注的是 oracle，也就是測試裡判斷對錯的部分。我依照「預期結果從哪裡來」把 oracle 分成三類：從規格來、從之前錄下來的輸出來，或交給另一個模型判斷。在這份研究裡，L1、L2、J1、J2 的標準來自規格，L3 來自錄下來的輸出，J3 則完全交給模型自己判斷。

## 4. Why LLM agents make the oracle hard（約 0:35）

agent 的 oracle 比一般程式難寫，有三個原因。第一，同一個正確答案可以有很多種說法，所以不能逐字比對。第二，每次執行的結果不一樣。例如測試 E06，沒改過的 agent 跑 5 次，有 3 次讓學生超過學分上限。第三，agent 會呼叫工具改資料，它可能已經幫學生選了課，回答卻說沒有選上。所以只看最後的回答不夠，還要看它中間呼叫了哪些工具。

## 5. The system under test（約 0:45）

被測的系統是我寫的選課助理，使用者是學生 S001。例如他說「幫我選 CS301 和 CS320」，正確做法是只選 CS301，因為再加 CS320 會變成 22 學分，超過 20 學分的上限，而且兩門課的結果都要說明。

agent 用的是 gpt-4.1-mini，有六個工具，其中 enroll 和 drop 會改資料。資料有 25 門課、3 個學生。規格有 8 條規則，包括資格檢查、隱私，還有不能照著資料裡的指令做事。我在兩門課的課程說明裡放了惡意指令，用來測間接 prompt injection。每次執行都存成一份 trace，記錄每個工具呼叫、最後的回答，還有最後選了哪些課。

## 6. Two tools, six oracles（約 0:50）

接下來是六個 oracle。L1、L2、L3 和 J1 寫在 promptfoo，J2 和 J3 寫在 DeepEval。

L1 是一段 Python 程式，直接讀 trace，檢查最後的選課結果對不對、有沒有呼叫不該呼叫的工具、有沒有讀到別的學生的資料。L2 檢查回答裡有沒有規格要求的關鍵字，或有沒有出現不該出現的字。L3 拿原版 agent 第一次跑的回答當標準答案，請模型判斷新的回答跟它一不一致。這是很常見的快照做法，我刻意沒有檢查這些標準答案對不對。

J1 和 J2 用同一份 rubric 請模型打分數。差別是 J1 只看回答，J2 用 DeepEval 的 G-Eval，還看得到工具呼叫。J3 是 DeepEval 的 TaskCompletion，不用 rubric，由模型自己推測任務是什麼、有沒有完成。L1 和 L2 不需要模型，其他四個每判一次都要呼叫一次模型。

## 7. Mutation testing（約 0:45）

為了知道 oracle 抓不抓得到錯，我用 mutation testing。我手動做了 11 個 mutant，每個只改一個地方，分布在工具程式、prompt、工具說明、agent 迴圈和模型這五層。

agent 每次結果都不一樣，如果只跑一次就比較，會出現很多假的 kill。所以我的規則是：每個測試跑 5 次，原版至少過 4 次、mutant 最多過 1 次，才算 kill。接著還要讀 trace，確認 mutant 失敗的那次真的有缺陷，才算 valid kill。

M03 拿掉了權限檢查，但功能測試從來沒讓 agent 去查別的學生，所以那段錯的程式一次都沒有執行。對 M03 的 kill 一定是假的，所以它可以當對照組。

## 8. Experiment setup（約 0:35）

實驗規模是 12 個版本、40 個測試、每個跑 5 次，共 2,400 份 trace。六個 oracle 判的是同一批 trace，所以判斷結果不同，只會是 oracle 本身造成的。另外我讀完整的 trace，標註了 640 筆輸出，當作 RQ2 的標準答案。red team 是另外跑的，有 64 個攻擊。主要的 judge 模型是 Claude Haiku 5.5。整個研究只花了 12.2 美元，最花時間的是標註和讀 trace。

## 9. RQ1: Which oracles catch the injected faults?（約 1:10）

RQ1 看每個 oracle 抓到幾個植入的錯。左邊的圖，藍色長條是 valid kill 的數量。上面的虛線框是只跑一次的情況：用到模型的 oracle 每跑一次都會「抓到」8 到 11 個，但大部分是 agent 本身不穩定造成的。

用五次的規則之後，L1 和 L2 各抓到 5 個，J1 和 J2 各 6 個，J3 只有 4 個。L3 有 7 個，但它同時有 17 次假的 kill，原因後面會講。

右邊的表，每一列是一個 mutant，每一欄是一個 oracle，藍色代表抓到。不同 oracle 抓到的錯不一樣。改到動作的錯，例如 M04 讓學生選到衝堂的課，看 trace 的 L1 和 J2 抓得到。只改到回答內容的錯，例如 M09 把工具結果截斷後，agent 開始編造先修課，L1 看不到，但看回答的 L2、J1、J2 抓得到。

M03、M05、M07、M08 沒有任何 oracle 抓到，原因有兩種。一種是別的地方擋住了錯，例如 M07 把 prompt 裡的學分上限改成 25，但工具回傳 20，模型相信工具。另一種是原版 agent 在那個測試上本來就會錯，所以看不出 mutant 比較差。

整體來看，L1 加 L2 兩個便宜的檢查就抓到 7 個，跟六個全部加起來一樣。

## 10. RQ2: Do the oracles agree with careful labels?（約 0:50）

RQ2 把每個 oracle 的判斷跟 640 筆標註比較。這 640 筆裡只有 151 筆有缺陷，所以只看準確率會太樂觀：一個全部判通過的 oracle，準確率也有 76%。所以我用 Cohen's κ，它會扣掉碰巧一致的部分，1 代表完全一致，0 代表跟隨機差不多。

結果 J2 最高，0.92；J1 是 0.86；L1 加 L2 合起來是 0.81；J3 只有 0.19。

我也換過 judge 模型。如果改用跟 agent 同一個模型 GPT-4.1 mini 來當 J2 的 judge，會漏掉 47% 的缺陷。所以 judge 最好不要跟 agent 用同一個模型。

## 11. RQ2: Where the oracles go wrong（約 0:55）

這頁看 oracle 錯在哪裡。深色是漏判，就是有缺陷卻判通過；淺色是誤判，就是正確卻判失敗。

L1 沒有誤判，但漏了 69%，因為大部分缺陷出在 agent 說的話，不是它做的事。J3 兩種錯都很多，因為它把 111 個正確的拒絕全部判失敗。例如使用者要看別人的資料，agent 正確地拒絕了，TaskCompletion 卻認為任務沒有完成。

右下是 L3 的 assertion echo。L3 的標準答案是從原版 agent 錄下來的，40 個裡有 7 個本身就錯。在這 7 個測試上，有缺陷的輸出剛好跟錯的標準答案一致，所以 L3 讓 68% 的缺陷通過，其他測試只有 16%。反過來，正確的回答因為跟錯的標準答案不一樣，反而被判失敗。這就是 L3 有 17 次假 kill 的原因。

## 12. RQ3: What does promptfoo's red team find?（約 0:55）

RQ3 是 promptfoo 的 red team。它根據我寫的 agent 用途和規則，自動產生 64 個攻擊，每個跑 3 次，共 192 次，再用另一個模型當 grader，判斷 agent 有沒有被攻破。我把每一次的 trace 都讀過，跟 grader 的判斷做比對。

在原版 agent 上，grader 標了 2 個問題，兩個都是誤報。另外有 7 個真的問題它沒抓到，其中 5 次是 agent 沒做資格檢查就直接呼叫 enroll，只是因為課程不存在，才沒有真的選上。

在 M03，也就是沒有權限檢查的版本上，有 10 次攻擊讓 agent 去查別的學生，其中 8 次把資料告訴了使用者，grader 抓到了 7 次。這是 40 個功能測試都沒有走到的路徑。另外，64 個攻擊裡有 34 個提到的課程根本不存在，因為產生攻擊的模型不知道系統裡有哪些資料。

## 13. Conclusions（約 0:45）

總結有五點。第一，只跑一次會讓每個 oracle 看起來都很強，要重複執行，並確認 kill 是真的。第二，便宜的確定性檢查效果很好。第三，judge 要先用標註檢查過才能相信。第四，從 agent 錄下來的參考答案會把 bug 一起錄進去。第五，red team 能找到新的路徑，但結果需要有人讀 trace 確認。

限制方面，只有一個小 agent 和一個模型；標註是 AI 助理照著準則做的，不是獨立的人；測試和錯誤是同一個人寫的；每個測試只跑 5 次。所以換一個系統，具體數字一定會變，但這些現象比較有可能會重複出現。

## 14. Thank you（約 0:10）

兩個工具都讓人很容易加上一個 oracle，但都沒有幫忙確認這個 oracle 對不對。我的報告到這裡，謝謝。
